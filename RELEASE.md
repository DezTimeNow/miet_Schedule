# Сборка и выпуск

Документ для того, кто продолжает поддерживать проект. Обычному пользователю
приложения ничего отсюда не нужно.

## Требования

- JDK 17
- Android SDK: platform 35, build-tools 34.0.0
- `ANDROID_HOME` указывает на каталог SDK

Версии инструментов зафиксированы в проекте. Менять их без необходимости
не стоит.

## Подготовка окружения

Склонировать репозиторий, указать в `local.properties` путь к своему SDK,
выполнить сборку. Сам Gradle подтянет нужные версии.

`local.properties` в репозиторий не попадает: в нём путь к SDK конкретной
машины.

## Обычная сборка

```bash
./gradlew assembleDebug
./gradlew testDebugUnitTest
```

Отчёт о тестах Gradle складывает в `app/build/reports`.

Тесты обязаны проходить до выпуска. На текущий момент их около трёхсот,
и они покрывают расчёт дней недели, расписания, напоминаний и обновлений.

## Релизная сборка

**Релиз собирается задачей `assembleRelease`, а не `assembleDebug`.**

Отладочная сборка помечена в манифесте как `android:debuggable="true"`: к
такому приложению можно подключить отладчик, его данные проще вытащить, и оно
заметно больше по размеру — в 0.72–0.74 так и вышло: 19,5 МБ вместо 13,8 МБ,
и это ушло пользователям. Отладочную сборку нельзя подписывать и выпускать,
даже если файл называется `release`.

```bash
./gradlew assembleRelease
```

Проверка после подписи, что флаг не просочился в выпуск:

```bash
$ANDROID_HOME/build-tools/34.0.0/aapt dump xmltree MIET-Schedule-0.N-release.apk \
  AndroidManifest.xml | grep -i debuggable
```

Команда не должна ничего вывести. Если вывела `android:debuggable` — собрана
не та сборка, выпускать нельзя.

## Подпись

В Gradle-конфигурации блока подписи нет намеренно: приложение подписывается
отдельно, после сборки. Так подпись остаётся постоянной независимо от
настроек сборки.

Сборка релизного APK сама по себе не даёт установочный файл — его нужно
подписать. Подпись делается утилитой `apksigner` ключом, который лежит **вне
репозитория**.

Ключ — часть закрытого окружения. Он хранится на диске разработчика и в
резервной копии отдельно от проекта. В репозитории, в документации и в
истории коммитов его быть не должно.

Проверить, каким сертификатом подписан APK, можно командой `apksigner
verify --print-certs`. Сверяться следует с резервной копией ключа, а не с
записью в документации.

## Ключ подписи

Android сверяет сертификат при установке. Из этого следует главное
правило выпуска:

**Ключ подписи нельзя терять и нельзя менять.**

Если выпустить APK с другим ключом, он не встанет поверх уже установленного:
система сочтёт его чужим приложением и потребует сначала удалить старое.
Данные пользователя при этом теряются, а обновление для всех, кто уже
установил прежнюю версию, становится невозможным.

Поэтому:

1. Резервная копия ключа обязана существовать **вне сервера**. Хранить ключ
   в репозитории нельзя.
2. Если ключ утрачен, вариант остаётся один: сменить `applicationId`, и тогда
   приложение станет новым и установится рядом со старым.

## Порядок выпуска

1. Поднять версию в `app/build.gradle.kts`: `versionCode` — на единицу
   больше предыдущего, `versionName` — с суффиксом стадии (`-alpha`
   сейчас, `-beta` в будущем). Android сравнивает именно `versionCode`.

2. Прогнать тесты.

3. Собрать и подписать.

4. Проверить на устройстве. Обязательная проверка: новая версия должна
   вставать **поверх** ранее установленной, не требуя удаления. Это
   единственная проверка, которая подтверждает, что подпись в порядке.

5. Коммит, тег, публикация релиза.

## Особенности публикации

**Тег обязан совпадать с номером релиза** — без префикса `v` и без суффикса
стадии.

**Релиз должен быть помечен как latest, а не как prerelease.**
`UpdateChecker` читает только `/releases/latest`, поэтому релиз с другой
пометкой до пользователей не дойдёт: приложение просто не увидит обновления.

## Что попадает в описание релиза

- буллиты с изменениями, по одной строке на изменение;
- контрольная сумма APK, чтобы пользователь мог проверить файл;
- **без фамилий, имён и номеров групп** — расписание содержит персональные
  данные студентов и преподавателей.

## Серверная часть

Часть функций полагается на Google Apps Script, исходники которого лежат в
`game_top.gs`: таблица рекордов мини-игры и счётчик установок.

**Развернуть его может только владелец скрипта.** Без доступа к аккаунту, под
которым он создан, скрипт не обновить, и правки останутся незадействованными.
Порядок всегда один: сначала изменение в репозитории, потом развёртывание.

## Кэш и нагрузка на сайт

`CachePolicy` держит два срока, и они обязаны совпадать: сколько кэш
считается свежим и как часто фоновая задача проверяет обновления. Сейчас оба
равны шести часам.

Фоновая задача ходит на сайт только за избранными группами и за текущей.
Кнопка «Обновить всё» перебирает все группы и создаёт заметную нагрузку,
поэтому её стоит вызывать осознанно.

Если число пользователей вырастет, первое, что нужно сделать, — разнести
период фоновой задачи случайной задержкой, иначе приложения, установленные
в один день, будут обновляться синхронно.

## Структура проекта

Основной код лежит в одном пакете и разделён по экранам и по слоям.

```
app/src/main/java/com/mietschedule/app/   экраны, логика, сеть, фоновые задачи
  *Ui.kt, *Screen.kt                       экраны
  MietApi.kt, ApiPaths.kt, Models.kt        сеть и модели
  UpdateChecker.kt, UpdateDialog.kt         обновления
  ReminderScheduler.kt, RefreshWorker.kt    уведомления и фон
game_top.gs                                серверная часть Apps Script
docs/                                      скриншоты для README
```

Названия файлов говорят за себя; назначение каждого видно по содержимому.
